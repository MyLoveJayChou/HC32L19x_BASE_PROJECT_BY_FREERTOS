## 1. 编码前先思考
**不要擅自假设。不要掩盖困惑。要说明取舍。**

实现之前：
- 明确说明你的假设。如果不确定，就提问。
- 如果存在多种理解方式，要把它们列出来，不要悄悄选择其中一种。
- 如果存在更简单的方案，要说出来。必要时应提出不同意见。
- 如果某件事不清楚，就停下来，指出哪里不清楚，并提问。

## 2. 简单优先
**用能解决问题的最少代码。不要做推测性设计。**

- 不添加用户没有要求的功能。
- 不为只使用一次的代码抽象出额外结构。
- 不添加未被要求的“灵活性”或“可配置性”。
- 不为不可能出现的场景添加错误处理。
- 如果写了 200 行但 50 行就能解决，应重写并简化。
- 引入设计模式、函数指针或不透明指针前，必须确认它能降低复杂度或匹配已有架构；不能为了形式上的“优雅”过度设计。

问自己：“资深工程师会不会认为这过度复杂？”如果答案是会，就简化。

## 3. 精准修改
**只修改必须修改的地方。只清理自己造成的问题。**

编辑已有代码时：
- 不要顺手“改进”相邻代码、注释或格式。
- 不要重构没有问题的代码。
- 遵循现有代码风格，即使你个人会用另一种写法。
- 如果发现无关的废弃代码，可以提到它，但不要删除它。

当你的修改造成孤立代码时：
- 删除因你的修改而变得未使用的 import、变量或函数。
- 不要删除修改前就已经存在的废弃代码，除非用户明确要求。

检验标准：每一行改动都应该能直接对应到用户的请求。

## 4. 目标驱动执行
**定义成功标准。持续迭代，直到完成验证。**

把任务转化为可验证的目标：
- “添加校验” -> “为非法输入编写测试，然后让测试通过”
- “修复 bug” -> “编写一个能复现 bug 的测试，然后让测试通过”
- “重构 X” -> “确保重构前后测试都通过”

对于多步骤任务，先给出简短计划：
```text
1. [步骤] -> 验证：[检查项]
2. [步骤] -> 验证：[检查项]
3. [步骤] -> 验证：[检查项]
```

清晰的成功标准能让你独立迭代。模糊的标准，比如“让它能用”，通常需要反复澄清。

## 5. 核心编码规范
**代码要保持一致、可读、便于审查。**

### 5.1 行宽限制
- 代码列数绝对不能超过 80 列。
- 任何超过 80 列的代码必须进行合理的换行和缩进。

### 5.2 对齐与换行
- 相邻行的等号、变量声明、结构体成员、宏定义等必须垂直对齐。
- 函数参数换行遵循示例规则：
  - 单参数且不超过 80 列：不换行。
  - 单参数且超过 80 列：参数换到下一行。
  - 多参数且首个参数后仍不超过 80 列：首个参数保留首行，其余参数换行对齐。
  - 多参数且首个参数后已超过 80 列：所有参数换行对齐。
- 参数换行后，参数类型和参数名应保持整齐对齐。

### 5.3 大括号风格
- 函数、`if`、`else`、`for`、`while` 等全部使用次行大括号风格。
- 不允许使用同行大括号风格。

### 5.4 安全与健壮性
- 函数内部如果有参数传入，必须在函数最开头检查其合法性。
- 条件判定中存在常量、宏定义或魔法数字时，常量必须左置。
- 示例：使用 `NULL == self`，不要使用 `self == NULL`。
- 示例：使用 `3U > count`，不要使用 `count < 3U`。

### 5.5 命名规范
- 命名必须统一。
- 变量、函数、结构体、枚举等命名严格使用全小写加下划线风格。
- 示例：`sensor_read_value`。

### 5.6 注释规范
- 必须包含必要注释，并严格遵循 Doxygen 规范。
- 文件头、函数、结构体、枚举和复杂逻辑必须使用 Doxygen 注释。
- 函数注释必须包含 `@brief`、`@param`、`@return` 等必要字段。
- 除非用户明确要求使用其他语言，注释默认一律使用中文。
- 注释应简洁，不要堆砌无意义的步骤说明。
- 不要添加解释显而易见逻辑的废话注释。
- 凡是生成、补充或修改带文件头作者信息的代码文件，`@author` 必须固定写为 `RUST HUEY`。

### 5.7 结构体声明
- 能使用前向声明时，优先使用前向声明。
- 不要在函数指针参数中反复直接书写 `struct xxx`，优先使用类型别名。

## 6. 架构与设计
**保持高内聚、低耦合，避免隐藏状态。**

- 用 C 语言编写代码时，要保持面向对象意识。
- 优先使用结构体封装对象状态和属性。
- 需要多态或可替换行为时，可使用函数指针模拟方法。
- 需要隐藏实现细节时，可使用不透明指针。
- 生成代码时必须主动考虑是否存在合适的设计模式或数据结构。
- 只有当设计模式能带来清晰边界、降低耦合或复用价值时才引入。

示例：
```c
/**
 * @brief 读取传感器数值。
 *
 * @param sensor_id 传感器标识。
 * @return 读取到的数值，失败时返回负数错误码。
 */
int sensor_read_value(uint8_t sensor_id)
{
    int value  = 0;
    int status = 0;

    status = sensor_driver_read(sensor_id, &value);
    if (0 != status)
    {
        return status;
    }

    return value;
}
```
